Terraform statefile(terraform.tfstate):-
1. Terraform must store state about your managed infrastructure and configuration. This state is used by Terraform to map real world resources to your configuration, keep track of metadata, and to improve performance for large infrastructures.
2. This statefile will be modified whenever you execute terraform commands that will impact the real world infra
eg:- terraform apply, terraform destroy
3. It is also used for team collaboration.

Local Statefile:- the file that exists in ur local machine when u execute tf apply
Remote Statefile:- the statefile automatically uploadded to AWS s3 or azure storage. it must be specifies in .tf files then only it will push the code to s3. It avoids dupliaction of resources when multiple people are working

Local statefile Disadvantages:-
“The main disadvantages of Terraform local state are:”
1. No collaboration support
• State is stored locally, so teams cannot share it
• Leads to inconsistencies and duplicate resource creation
2. No state locking
• Multiple users running Terraform simultaneously can corrupt the state
3. Risk of state loss
• If the local file is deleted or corrupted, Terraform loses track of infrastructure
4. Security concerns
• State file may contain sensitive data and is not encrypted by default

✅ Step-by-step flow
1. Read the state file
• What Terraform thinks exists
2. Refresh (very important step)
• Connects to cloud (AWS/Azure)
• Gets actual infrastructure state
• Updates state in memory (not final yet)
3. Compare 3 things
• Your .tf configuration
• Refreshed real infrastructure
• State file
4. Create an execution plan
• What needs to be created/updated/deleted
5. Apply changes to infrastructure
• This is where actual resources are modified
6. Update state file (final step)
• After successful changes, state file is written

🔹 Simple explanation
• Memory = RAM (temporary working space)
• State file (terraform.tfstate) = permanent storage on disk

State Locking in terraform:-
State locking ensures that only one Terraform operation can modify the state at a time, preventing conflicts and corruption
🔴 Why is it Needed?
Terraform state is a single source of truth.
👉 If two people run terraform apply simultaneously:
• Both try to update the state file
• Leads to race conditions
• Results in corrupted or inconsistent infrastructure

🧠 Real-Time Scenario
• You run terraform apply
• Your teammate tries at the same time
👉 Terraform will show:
“Error: state is locked”
This prevents:
• Duplicate resources
• State corruption

🔍 When Locking Happens (Important)
State locking is used for commands that touch the state:
• terraform plan → reads state
• terraform apply → modifies state
• terraform destroy → modifies state
• terraform refresh → updates state

DynamoDB statelocking
“DynamoDB is used by Terraform to maintain a lock record so that only one user can modify the state file at a time.”

👉 Here’s what happens:
1. Terraform tries to run apply
2. It creates a lock entry (row) in DynamoDB table
3. If the lock exists → other users are blocked
4. After completion → lock entry is deleted

🔍 What’s Inside the DynamoDB Table?
• Lock ID
• Operation (apply/plan)
• Who locked it
• Timestamp

Resource Attribute references:-
In Terraform, resource attribute references are how you use values from one resource inside another resource.
Think of it like:
👉 “Take output from Resource A → use it in Resource B”In Terraform, resource attribute references are how you use values from one resource inside another resource.

example:-
# Step 1: Create a VPC
resource "aws_vpc" "main_vpc" {
 cidr_block = "10.0.0.0/16"
}
# Step 2: Create a Subnet inside that VPC
resource "aws_subnet" "subnet1" {
 vpc_id     = aws_vpc.main_vpc.id   # 🔥 Resource Attribute Reference
 cidr_block = "10.0.1.0/24"
}
# Step 3: Create an EC2 Instance inside that Subnet
resource "aws_instance" "web_server" {
 ami           = "ami-12345678"
 instance_type = "t2.micro"
 subnet_id     = aws_subnet.subnet1.id   # 🔥 Another Reference
}
# Step 4: Output the Public IP of the Instance
output "instance_public_ip" {
 value = aws_instance.web_server.public_ip   # 🔥 Attribute Reference
}

Data Sources:-
Think of it like this:
• resource block → creates something
• data block → reads something that already exists
⸻
🔹 Why do we use data sources?
You use data sources when:
• Infrastructure already exists (created manually or by another Terraform project)
• You want to reuse existing values (like VPC IDs, AMI IDs, subnets, etc.)
• You don’t want Terraform to manage (create/delete) that resource

example:-
🧩 Scenario (Very realistic in companies)
• Network team already created a VPC
• Your repo only creates:
• EC2 instance
• Subnet (optional)
👉 You should NOT recreate VPC
👉 You will fetch it using a data source

data.tf:-
# Fetch existing VPC
data "aws_vpc" "existing_vpc" {
 filter {
   name   = "tag:Name"
   values = ["prod-vpc"]
 }
}
# Fetch existing subnet
data "aws_subnet" "existing_subnet" {
 filter {
   name   = "tag:Name"
   values = ["prod-subnet"]
 }
}
# Fetch latest AMI
data "aws_ami" "latest_ami" {
 most_recent = true
 owners      = ["amazon"]
 filter {
   name   = "name"
   values = ["amzn2-ami-hvm-*"]
 }
}

ec2.tf
resource "aws_instance" "my_ec2" {
 ami           = data.aws_ami.latest_ami.id
 instance_type = "t2.micro"
 subnet_id = data.aws_subnet.existing_subnet.id
 tags = {
   Name = "my-ec2"
 }
}

TERRAFORM PROVISIONERS:-
Video:- https://www.youtube.com/watch?v=U_jTWB8Ma6I
1. Terraform is used for infrastructure deployment, whereas provisioners are used for infrastructure management.
2. These provisioners cannot perform huge tasks like the configuration management tools such as Ansible, chef or puppet.
3.  Provisioners allow you to execute commands or scripts on remote resources or on the local machine where Terraform is run. For example, the remote-exec provisioner can be used to execute a bash script immediately after a resource is created.
3. Why use provisioners?
Examples:
Install packages on a newly created VM
Copy configuration files to a server
Run shell scripts after infrastructure deployment
Perform cleanup tasks before resource destruction

NOTE:- Use Terraform provisioners only for lightweight, one-time post-provisioning actions when no provider-native or configuration-management solution exists. For server configuration, software installation, patching, compliance, and ongoing state management, use dedicated configuration tools such as Ansible, Puppet, or Chef. Terraform provisions infrastructure, while configuration management tools configure and maintain it.
Use provisioners only for small, one-time actions that happen immediately after a resource is created or just before it is destroyed, and when there is no better native option available. HashiCorp explicitly recommends provisioners as a "last resort."

There are 3 types of Provisioners:-
1. Local-exec
2. File
3. Remote-exec

1. file Provisioner:-
The file provisioner copies files or directories from the machine running Terraform to the target resource (VM/server). eg:- github actions runner or laptop
eg:-
resource "aws_instance" "web" {
  ami           = "ami-12345"
  instance_type = "t2.micro"
  provisioner "file" {
    source      = "app.conf"
    destination = "/tmp/app.conf"
  }
  connection {
    type        = "ssh"
    user        = "ec2-user"
    private_key = file("key.pem")
    host        = self.public_ip
  }
}

2. local-exec provisioner:-
Runs a command on the machine where Terraform is executing.
The value of local-exec is that it can use information generated during Terraform execution and perform actions automatically as part of the deployment workflow.
That could be:
Your laptop
Azure DevOps agent
GitHub Actions runner
Jenkins server
eg:-
resource "aws_instance" "web" {
  provisioner "local-exec" {
    command = "echo VM Created Successfully"
  }
}

3. remote-exec provisioner:-
Runs commands directly on the remote server after Terraform creates it.
resource "aws_instance" "web" {
  ami           = "ami-12345"
  instance_type = "t2.micro"
  provisioner "remote-exec" {
    inline = [
      "sudo yum update -y",
      "sudo yum install nginx -y",
      "sudo systemctl start nginx"
    ]
  }
  connection {
    type        = "ssh"
    user        = "ec2-user"
    private_key = file("key.pem")
    host        = self.public_ip
  }
}

NOTE:- Connection block is required to connect to the VMs or resources that terraform created, terraform only knows about the resource name, id , public ip, private ip.
It is not aware how to connect to the VM, so connection block is mandatory.

TERRAFORM DRIFT:-(Video:- https://www.youtube.com/watch?v=W_8wYhF6DnQ)
I have created an AWS resource with instance-type "t2.micro" using terraform configuration files in the github for the application "payments".
This resources was facing some issues so the developer changed the instance-type to "t2.small" from AWS management console and that change was not updated in the github TF file.
The difference between the desired state which is terraform configuration files in the github and the actual state of the AWS infra is called drift.

What is the drawback of this?
You might assume that as the instance type has been changed application is running fine then what is the issue?
The real issue is if tomorrow someone want to modify some other property like tags of the aws instance and he might do that using terraform configuration files.
In this case the existing t2.small might get updated back to t2.micro as the drift still exists.
NOTE:- Terraform plan will display the changes that it will make to actual infrastructure, so pay attention to that

How terraform detects drift?
when we run "terraform plan"
Terraform:
Reads the state file
Queries AWS/Azure/GCP APIs
Compares actual infrastructure with desired configuration

+:- create new one
-;- delete
~;- update
-/+:- delete and then create

how to Resolve the drift?
1. Check who made the change in the infrastructure using AWS cloudtrail.
1. If Terraform configuration is the source of truth, then do "terraform apply"
2. If the manual change was intentional, update the terraform configuration files manually and then terraform apply.
